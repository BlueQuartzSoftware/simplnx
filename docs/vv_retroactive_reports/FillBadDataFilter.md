## Oracle classification (tentative)

- **Recommended class:** **4 (Invariant-based)** as primary, with **1 (Analytical)** for the small hand-built fixtures (Test11 in particular is essentially analytical — a 3×3×3 known geometry).
- **Rationale:** This filter is morphological in nature: it grows valid feature regions into adjacent bad-data voxels iteratively. Strong invariants exist:
  - **Total voxel count is preserved** — Phase 4 only reassigns FeatureIds; it does not add or remove tuples.
  - **Monotonicity** — count of voxels with `FeatureId > 0` is non-decreasing per Phase-4 iteration; count of voxels with `FeatureId == -1` is strictly decreasing each iteration until 0.
  - **Convergence** — Phase 4's `while(count != 0)` terminates because each iteration that has any neighbor-of-bad-voxel reduces `count` by at least one; the loop is a proven dilation.
  - **Idempotence on a fully-good volume** — if no voxel has `FeatureId == 0`, Phases 1–3 produce empty `provisionalLabels` and Phase 4's `count` is 0 immediately; output equals input.
  - **Set-of-features property** — after the run, `{FeatureId values present}` is a subset of `{0} ∪ {original FeatureIds present}` (or with `+1` if `storeAsNewPhase`). No new feature IDs are invented except the optional new-phase index.
  - **Region-classification correctness** — for each connected component of bad voxels, all voxels in that component receive the same fate (filled or kept), determined solely by component size vs. threshold.
  - **Tie-break determinism** — Test11 already locks this in.
  Class 3 (Paper-based) is **not appropriate** — there is no canonical paper for this morphological dilation; it is a project-specific cleanup heuristic.
- **Action required:** Developer to defend or replace the Class-4 recommendation. Promote the implicit invariants above into explicit `REQUIRE(...)` assertions in the existing tests so the tests *are* the oracle of record.

## Recommended Deviation entries (proposed, pending legacy comparison)

> **Deviation ID:** `FillBadData-D1`
> **Filter UUID:** `a59eb864-9e6b-40bb-9292-e5281b0b4f3e`
> **Symptom (proposed, needs verification):** SIMPLNX may differ from SIMPL 6.5.171 on the assignment of `CellPhases` for large-defect voxels when `StoreAsNewPhase=true`. SIMPLNX assigns *one* new phase index (`maxPhase + 1`) to *all* large-defect regions, regardless of whether they are connected. Legacy may have assigned a unique new phase index per connected large region.
> **Root cause:** SIMPLNX `phaseThreeRelabeling` uses a single `(*cellPhasesPtr)[index] = static_cast<int32>(maxPhase) + 1;` for every voxel that is not in `localSmallRegions`. There is no per-region counter.
> **Affected users:** Anyone whose downstream analysis treats each large defect as a distinct "phase" and counts phases.
> **Recommendation:** Confirm legacy behavior. If legacy uses `maxPhase + 1, maxPhase + 2, …` per region, document the deviation and decide whether to align SIMPLNX with legacy or keep the simpler current behavior.
> **Status:** Proposed — pending verification.

> **Deviation ID:** `FillBadData-D2`
> **Filter UUID:** `a59eb864-9e6b-40bb-9292-e5281b0b4f3e`
> **Symptom (proposed, needs verification):** Phase-4 tie-break order may differ from legacy. SIMPLNX iterates faceNeighbors in `faceNeighborInternalIdx` order (defined by `NeighborUtilities`) and assigns the neighbor with the most votes; on a tie, the first feature to *reach* the highest count wins (line 628: `if(current > most)` is strict-greater). Legacy SIMPL may have used a different ordering (e.g., −Z, −Y, −X, +X, +Y, +Z literal sequence) producing a different winner on ties.
> **Root cause:** Vote-loop's strict-greater comparison combined with neighbor-iteration order makes the result depend on the ordering convention. PR #1523 changed this from inline literals to a shared utility — silently re-orderable.
> **Affected users:** Anyone reproducing exact legacy output on small defects with multiple equally-frequent neighbor features. Test11 already locks in the SIMPLNX choice.
> **Recommendation:** Compare against legacy on Test11's exact input. If output differs, document the deviation; SIMPLNX's tie-break is locked by Test11 and should not be regressed.
> **Status:** Proposed — pending verification.

> **Deviation ID:** `FillBadData-D3`
> **Filter UUID:** `a59eb864-9e6b-40bb-9292-e5281b0b4f3e`
> **Symptom (proposed, needs verification):** SIMPLNX iterates Phase-4 iteratively until `count == 0` (i.e., until every −1 voxel is filled), with no max-iteration cap. Legacy SIMPL behavior is unconfirmed — it may have had a fixed iteration count or a "no progress" early-exit.
> **Root cause:** `phaseFourIterativeFill`'s `while(count != 0)` loop has no upper bound. On a pathological input (e.g., a fully-bad slab with no positive neighbors anywhere), the loop would either spin forever or exit if no progress is made. Inspecting the code: if no voxel changes in an iteration, `count` is unchanged from the previous iteration *but* Pass 1 doesn't change `featureIdsStore` — Pass 2 does (via `FillBadDataUpdateTuples`). If `neighbors[]` stays at `-1` for all bad voxels (no positive neighbor found), `FillBadDataUpdateTuples`'s skip-self check (`if(neighbor == tupleIndex) continue;`) means nothing gets written — and the next iteration `count` is identical. **Potential infinite loop on isolated bad regions with zero positive neighbors.**
> **Affected users:** Anyone running on data where a connected −1 region is entirely surrounded by other −1 voxels or by image boundaries (no positive neighbors reachable). Phase 3's classification means this can only happen if the whole image is bad-data.
> **Recommendation:** Add a "no-progress" termination check (compare `count` to the previous iteration's `count`; if equal and non-zero, abort with a clear error). Document in test.
> **Status:** Proposed — needs verification both against legacy and as a defensive code change.

> **Deviation ID:** `FillBadData-D4`
> **Filter UUID:** `a59eb864-9e6b-40bb-9292-e5281b0b4f3e`
> **Symptom (proposed, needs verification):** Phase 3's small-vs-large classification uses a signed-int cast: `static_cast<int32>(size) < m_InputValues->minAllowedDefectSizeValue` (line 476 of `FillBadData.cpp`). For a connected bad-region larger than `INT32_MAX` voxels (~2.1e9 voxels, theoretically reachable for very large OOC volumes), the cast wraps to a negative value and the test classifies the region as **small** (will be filled).
> **Root cause:** Type-narrowing cast without bounds check.
> **Affected users:** Anyone running on >2 billion-voxel volumes with massive contiguous bad regions. Edge case but reachable in OOC workflows.
> **Recommendation:** Compare directly: `size < static_cast<uint64>(m_InputValues->minAllowedDefectSizeValue)`. Cheap to fix.
> **Status:** Proposed — implementation bug, not a legacy-deviation per se. Worth filing as its own bug fix PR independent of V&V.

## Bug-pattern check (per audit-wide note)

Inspected `FillBadData.cpp` for the divisor-bug-style "size reassigned inside an inner loop clobbering an earlier decrement" pattern that surfaced in sibling filters. **None found** — `FillBadData` is morphological, not feature-list-based; there are no `NeighborList::size()` calls. Phase 4's `count` variable is reset to 0 at the top of each iteration and incremented monotonically inside the loop without reassignment. The `featureNumber[]` vote array is reset per-voxel using a bounded second pass over the same neighbors that voted (lines 639–654), which is correct. **No bug-pattern hit.**

However, three independent issues surfaced during inspection — see Deviation entries D2, D3, and D4 above.
