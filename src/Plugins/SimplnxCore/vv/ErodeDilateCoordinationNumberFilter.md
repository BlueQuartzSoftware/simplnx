## Summary

`ErodeDilateCoordinationNumberFilter` counts, for every voxel in an `ImageGeometry`, how many of its six face neighbours lie across the bad/good boundary (`FeatureId == 0` vs `FeatureId > 0`); voxels whose count meets the `CoordinationNumber` threshold have every non-ignored cell array's tuple overwritten from the most-voted neighbour, optionally repeating until no voxel qualifies. Verification is **Class 1**: five 5×5×1 fixtures, exercised across eight `TEST_CASE`s with hand-derived expected output, replace the previous comparison against a DREAM3D-6.6-generated exemplar, and the result was then compared against DREAM3D 6.5.171 across a 27-combination parameter sweep covering every one of those five grids. **No output-affecting bugs found and no output deviations from 6.5.171**; all 11 test cases pass, 1330 assertions. Two robustness defects were fixed. First, `operator()()` stored `m_ShouldCancel` and never read it, so the (legacy-shared) `Loop = true` non-termination could not be interrupted from the GUI; a cancel check now runs at the outer sweep level. Second, per a requester decision on 2026-08-19 to uniformise preflight validation across the erode/dilate family — refined at final gate review to "errors or warns" once the non-termination was shown to be data-dependent at one of the two thresholds — `preflightImpl` now carries three outcomes: the legacy-parity interval check on `CoordinationNumber` (rewritten to name the offending value, `-16800`); a beyond-parity check **rejecting** `CoordinationNumber = 0` with `Loop` enabled (`-16801`), which is non-terminating on every possible input because the sweep's `coordination >= 0` stopping predicate is satisfied by every voxel of every volume; and a beyond-parity **warning** on `CoordinationNumber = 1` with `Loop` enabled (`-16802`), whose termination is data-dependent — a boundary-free volume always terminates as a single no-op sweep, while a volume containing a good/bad boundary may oscillate indefinitely — and which must therefore remain runnable. Together the latter two make SIMPLNX's accepted-input surface differ from 6.5.171, which accepts both unconditionally, so they are recorded as deviation `ErodeDilateCoordinationNumberFilter-D1`. None of the three changes any output: they act on input before any action is produced, and every previously-terminating combination still produces byte-identical results. Two further latent defects shared by both implementations remain documented for follow-up.

## Algorithm Relationship

**Port.**

*Evidence:* SIMPLNX inherits the legacy SIMPL UUID (`SimplnxCoreLegacyUUIDMapping.hpp:235` maps `d26e85ff-…` to this filter). `Algorithms/ErodeDilateCoordinationNumber.cpp` (190 lines) was read against the legacy `ErodeDilateCoordinationNumber::execute()` (`Source/Plugins/Processing/ProcessingFilters/ErodeDilateCoordinationNumber.cpp:150-347`) statement by statement; the two are the same algorithm with the same loop nesting.

**Port-time deltas.** Each is enumerated with a one-sentence justification of why it does not change output:

1. **Hand-rolled neighbour bookkeeping → `NeighborUtilities`.** Legacy builds `neighpoints[6]` inline and re-derives boundary validity with six `if(l == n && …)` tests in each of the two neighbour loops. SIMPLNX calls `initializeFaceNeighborOffsets` / `initializeFaceNeighborInternalIdx` / `computeValidFaceNeighbors` (`VoxelNeighbors<Image3D>`). The offsets, the traversal order (`-Z, -Y, -X, +X, +Y, +Z`), and the validity predicates are identical value-for-value; SIMPLNX simply computes the validity array once per voxel and reuses it in both loops. No output effect.
2. **`QList<QString> voxelArrayNames` → `GenerateDataArrayList`.** Both collect every cell array in the `FeatureIds` parent group and subtract the ignore list; SIMPLNX holds `shared_ptr<IDataArray>` instead of re-looking-up names. Same set, same transfer. No output effect.
3. **`IDataArray::copyTuple` → `ExecuteDataFunction(DataArrayCopyTupleFunctor{}, …)`.** SIMPLNX's `IArray` API has no virtual `copyTuple`, so the type is dispatched at runtime. `DataArrayCopyTupleFunctor` copies the `DataArray<T>` by value, which shares the underlying `m_DataStore` (`DataArray.hpp:153-157`), so the write lands on the real store. No output effect.
4. **`m_Neighbors` is `int32*` in legacy, `std::vector<int64>` in SIMPLNX.** A widening of the stored source index; identical for any volume legacy could address. No output effect.
5. **`int32_t current` hoisted out of the loop in legacy, declared per-iteration in SIMPLNX.** Legacy also resets it to 0 per voxel, and it is written before every read in both. No output effect.
6. **`AppendDataObjectModifications` in preflight.** SIMPLNX declares the in-place modification set to the pipeline; legacy has no equivalent concept. Metadata only. No output effect.
7. **Two further preflight outcomes on the low-`CoordinationNumber` + `Loop` region.** Added 2026-08-19; legacy validates only the `[0,6]` interval. The error at `CoordinationNumber = 0` **does** change which pipelines run — it is deviation `-D1` — but not what any running pipeline produces, since it rejects only a setting that never terminates in either version. The warning at `CoordinationNumber = 1` changes neither: it leaves the pipeline runnable and adds only a diagnostic. See Bug adjudication item 5.

**Material PRs since baseline:** none identified for this filter.

**Direction-parameter check.** The `ErodeDilateMask` / `ErodeDilateBadData` defect (X/Y/Z direction parameters declared but ignored) **cannot occur here**: this filter declares no direction parameters at all, in either SIMPLNX (`ErodeDilateCoordinationNumberFilter.cpp:56-68`) or legacy (`setupFilterParameters`, legacy `:69-85`). Verified rather than assumed, per the shared-context instruction.

`Loop ∈ {false, true}` is swept via `GENERATE` + `DYNAMIC_SECTION` in the four `CoordinationNumber = 4`/`5` fixtures and in the fixture-D `CoordinationNumber = 2` case. What `Loop = true` does differs by fixture and threshold and is asserted, not assumed:

- At `CoordinationNumber = 4` (fixtures A, B, C) the trailing counter loop re-reads the `coordinationNumber[]` array the sweep just filled, which still holds the **pre-copy** value 4 at the reassigned voxel — so the counter is **1**, not 0, and a second sweep runs. That second sweep finds no bad voxel, recomputes every coordination number as 0, and exits with the output unchanged.
- At `CoordinationNumber = 5` nothing is reassigned and the largest coordination number in the grid is 4, so the counter is 0 immediately and there is **no** second sweep.
- On fixture D at `CoordinationNumber = 2` the second sweep **does** change the output: sweep 1 leaves one bad voxel at index 18 that sweep 2 fills. This is the case that makes `Loop` observable at all, and it is why fixture D was added — in fixtures A, B and C the extra sweep is a no-op, so a build that ignored `Loop` entirely would pass every one of them.

The `CoordinationNumber = 1` and `CoordinationNumber = 0` fixtures pin `Loop = false` deliberately: both of these fixtures contain a good/bad boundary, and `Loop = true` at either threshold failed to terminate on those fixtures under a 45 s probe in both implementations (see the deviations doc). At `CoordinationNumber = 0` that non-termination is universal; at `CoordinationNumber = 1` it is data-dependent, and a boundary-free volume terminates immediately instead. Since 2026-08-19 SIMPLNX responds to the two thresholds differently, because they fail differently. `CoordinationNumber = 0` with `Loop` is **rejected at preflight** (Guard B, `-16801`, deviation `-D1`) — it cannot terminate on any input, so it is unreachable rather than merely untested. `CoordinationNumber = 1` with `Loop` is **accepted with a warning** (Guard C, `-16802`, same deviation) — it terminates on a boundary-free volume, which the fixtures deliberately are not, so it remains reachable and remains untested for *output* here; the warning, not the output, is what `Invalid Parameters` pins. That case also asserts, in a complementary section, that the `Loop = false` variants these two oracles depend on are still accepted **and silent**.

## Deviations from DREAM3D 6.5.171

**One open deviation: `ErodeDilateCoordinationNumberFilter-D1` (active). No *output* deviation observed on any runnable combination.**

`-D1` is not an A/B finding — it could not be, because it concerns the only settings the A/B was unable to run on its fixtures. `CoordinationNumber ∈ {0, 1}` with `Loop = true` failed to terminate in *either* binary on the boundary-bearing fixtures used, under a 45 s guard, and 6.5.171's `dataCheck()` permits both unconditionally. On 2026-08-19 the requester directed uniform preflight validation across the erode/dilate family, refined at final gate review to "errors or warns", and SIMPLNX now treats the two thresholds according to how they fail. `CoordinationNumber = 0` with `Loop` is **rejected** (`-16801`): its stopping predicate `coordination >= 0` is satisfied by every voxel of every volume, so no input exists on which it converges and refusing it forfeits nothing. `CoordinationNumber = 1` with `Loop` is **warned** (`-16802`) and still runs: its predicate is satisfied only by boundary voxels, so termination is data-dependent — it always completes as a single no-op sweep on a volume with no boundary, and it *may* oscillate indefinitely on one that has a boundary — a boundary-free volume being a realistic post-cleanup input that a 6.5.171 pipeline could and did run to completion. Rejecting that one would have broken working legacy pipelines. Both are user-visible differences in accepted input, so they are written up together as a deviation with `Recommendation: Trust SIMPLNX` rather than recorded merely as an improvement. Both are output-neutral by construction: no combination that previously produced a result is affected, which the eight unchanged oracle test cases and the 54/54 A/B pairs below continue to demonstrate. The companion parity guard (`CoordinationNumber` outside `[0,6]`, `-16800`) is **not** a deviation — 6.5.171 rejects the same interval at `ErodeDilateCoordinationNumber.cpp:118-123` with code `-5555`; only the message text and the code number differ, and neither is part of the algorithm's contract.

Comparison run on all five fixtures (`single`, `seam`, `majority`, `loopdisc`, `reset`) across 27 parameter combinations, diffed element-wise on `FeatureIds` and on an index-encoded `CopiedValues` tracer: **54/54 (combination, array) pairs match exactly**, with **38 of the 54 on non-trivial output** (output ≠ input), so the match is not an artifact of both binaries doing nothing. The remaining **16** are no-ops: `CoordinationNumber ∈ {5, 6}` × `Loop ∈ {false, true}` × the `single` and `seam` fixtures = 8 combinations × 2 arrays, at thresholds those grids' maximum coordination number of 4 can never meet. (`results_compare.txt` and `results_compare_wave2.txt` label each pair, so the split is countable directly from the artifacts.)

See `src/Plugins/SimplnxCore/vv/deviations/ErodeDilateCoordinationNumberFilter.md` for the full `-D1` entry, for the non-deviations that were investigated and ruled out, and for the three latent defects that both implementations share — the `Loop = true` non-termination at low thresholds (its universal half now unreachable in SIMPLNX behind the `-D1` error and its data-dependent half now warned but still runnable; both still reachable and silent in 6.5.171), the `featureCount[0]` int32 overflow at extreme scale, and the negative-`FeatureId` wrap in the `numFeatures` scan that sizes the accumulator (`featureName > numFeatures` compares `int32` against `size_t`, so a `FeatureId` of -1 promotes to `SIZE_MAX`, `numFeatures + 1` wraps to 0, and `featureCount` is allocated empty; every later `featureCount[feature]++` is then out of bounds. Legacy sizes its accumulator identically — `size_t numfeatures` compared against `int32_t featurename` at legacy `:182-191`, feeding `QVector<int32_t> n(numfeatures + 1, 0)` at `:208` — so the exposure is shared and it is not a deviation).

## Bug adjudication

Two hypotheses were carried into this pass and three further defects were found during review. Items 1 and 2 are not SIMPLNX bugs; items 3 and 5 were fixed; item 4 is recorded for a future change.

**1. `featureCount` reset asymmetry — flagged as the single most likely defect.** The audit confirmed the asymmetry is real: `featureCount[0]` is incremented (`:129`) whenever a good voxel sees a bad neighbour, but the reset loop's `if(feature > 0)` guard (`:163-166`) never clears index 0, so it grows monotonically for the lifetime of the call. It **cannot** corrupt the neighbour choice: in the good-voxel branch every vote lands on the single key 0, so the comparison is only ever against successive values of that one counter, and both with and without the leak the counts increase strictly within a voxel, making the last qualifying neighbour the winner either way. `most` is reset per voxel, so a leaked base can never suppress the first vote. Legacy has the identical guard and identical leak. **Verdict: neither oracle error nor filter bug — a genuine but output-neutral asymmetry.** No code change. Full proof, and the residual int32-overflow concern at extreme scale, in the deviations doc.

**2. Tie-break determinism.** The code is deterministic: fixed traversal order plus a strictly-greater comparison means the first feature to reach the maximum vote count wins. Following the `#1687` precedent — where a tie-break hypothesis survived source comparison and was falsified only by the binaries — this was **not** acted on from the source read. The `seam` fixture was built to force a real 2-vs-2 tie, and both binaries independently produced `FeatureIds[12] == 1` with `CopiedValues[12] == 111`, naming source neighbour index 11 in both. **Verdict: not a bug; determinism confirmed by binary evidence on both sides.**

**3. Missing cancel check — fixed.** `ErodeDilateCoordinationNumber::operator()()` took `m_ShouldCancel` in its constructor, stored it, and exposed it through `getCancel()`, but **never read it**. Combined with the (legacy-shared) `Loop = true` non-termination at `CoordinationNumber ≤ 1`, that made an unbounded sweep uninterruptible from the DREAM3D-NX GUI: the flag the Cancel button sets was never consulted, so the only exit was killing the application. **Verdict: robustness defect in SIMPLNX.** Fixed in this PR by adding the house-standard early return at the top of the sweep's outer (z) loop — the same placement and form used by the sibling `Algorithms/ErodeDilateBadData.cpp:144-148` — so the check costs one atomic read per z-slice per sweep rather than one per voxel:

```cpp
if(m_ShouldCancel)
{
  return {};
}
```

Legacy 6.5.171 has no cancel check either (its `execute()` never tests `getCancel()`), so this is **not** a deviation from legacy behaviour — it is a SIMPLNX-side improvement over a shared weakness. No output-affecting change: on any terminating run the flag is never set, and all 11 test cases pass unchanged with the check in place.

The Path 20 guard added on 2026-08-19 (item 5 below) makes only the **universal** half of the spin unreachable in SIMPLNX — `CoordinationNumber = 0` with `Loop`. The data-dependent half, `CoordinationNumber = 1` with `Loop`, is deliberately still permitted (Guard C warns rather than rejects, because it terminates on a boundary-free volume), and on a volume containing a good/bad boundary it may oscillate indefinitely. For that still-reachable half this check is **not** defence in depth — it is the user's only escape short of killing the application, which is precisely why Guard C's message tells the user the run is cancellable. It costs one atomic read per z-slice per sweep, it is the house-standard form the sibling filters carry, and it additionally covers any future path — a larger volume, a different fixture, a later change to the stopping condition — that produces an unexpectedly long run.

Algorithm source modified by this V&V pass: `Algorithms/ErodeDilateCoordinationNumber.cpp` — the cancel check above, and nothing else. No change to the vote, the transfer, the reset, or the termination counter. Confirmed by `git diff` against the pre-pass file after every mutation experiment described in the Oracle section.

**4. Negative `FeatureId` wraps the accumulator sizing — found, not fixed.** `numFeatures` is `size_t` and is compared against an `int32` `featureName` (`:62-71`), so a negative id promotes to a huge unsigned value; a `FeatureId` of exactly -1 makes `numFeatures + 1` wrap to 0 and `featureCount` allocate empty, after which every `featureCount[feature]++` is out of bounds. Nothing in the parameter (`int32`, component shape `{1}`) or in `preflightImpl` constrains the values. **Verdict: latent robustness defect, shared with 6.5.171**, which sizes its `QVector<int32_t> n` from the identical signed/unsigned comparison. Not fixed in this cycle — the fix is an input-validation behaviour change that deserves its own change and its own test — and recorded as a shared latent defect in the deviations doc with a recommendation. (Item 5 below adds preflight validation of the *parameters*; it does not scan `FeatureIds` values, so this defect is untouched by it.)

**5. Non-terminating `Loop` was reachable from the UI with no diagnostic — addressed, and it is deviation `-D1`.** Both implementations can spin indefinitely at `CoordinationNumber ∈ {0, 1}` with `Loop = true` on a boundary-bearing volume (established by execution, not inference: both binaries killed at 45 s), and both accepted those settings silently. On 2026-08-19 the requester directed uniform preflight validation across the erode/dilate family, refined at final gate review to "errors or warns" once the two thresholds were shown to fail differently — `0` universally, `1` only on some volumes that contain a good/bad boundary, and never on one that does not. `preflightImpl` now carries three outcomes:
