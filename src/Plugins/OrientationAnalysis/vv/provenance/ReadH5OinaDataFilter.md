## How it was generated

The archive contains an Oxford Instruments AZtec vendor export, `H5Oina_Test_Data.h5oina`, and a `.dream3d` output generated by this filter. The test now reads only the vendor input and derives its expected values independently. `WriteH5OinaFixture` in `src/Plugins/OrientationAnalysis/test/ReadH5OinaDataTest.cpp` writes the small analytical inputs from explicit C++ scan specifications. The separate derivation script is `vv_work:ReadH5OinaDataFilter/h5oina_oracle.py`.

The vendor-file structure and values are recorded in `vv_work:ReadH5OinaDataFilter/probe_real_file.txt` and `vv_work:ReadH5OinaDataFilter/readback_real_file.txt`.

## Oracle provenance (Classes 2, 3, 5 only)

The Class 2 test reads the input datasets with H5Support::H5Lite and bypasses EbsdLib H5OINAReader. The separate Python script uses h5py for file reads and NumPy float32/float64 arithmetic for expected values. It does not execute the filter. The recorded vendor readback is independent of the generated `.dream3d` exemplar.

- **Library:** H5Support::H5Lite for the encoded readback; h5py and NumPy for the independent Python derivation.
- **Runtime:** C++ unit test and Python derivation script.
- **Random seed:** Not applicable; the fixtures use explicit values.
- **Script:** `vv_work:ReadH5OinaDataFilter/h5oina_oracle.py` (`spec` and `readback` modes).
- **Recorded output:** `vv_work:ReadH5OinaDataFilter/oracle_spec.txt` and `vv_work:ReadH5OinaDataFilter/readback_real_file.txt`.

The script's hexagonal condition covers Hexagonal-High. The current C++ option and multi-scan tests extend the same independent pi/6 expectations to Hexagonal-Low. EbsdLib is part of the system under test, not the reference implementation.

## Regenerated to fix a circular-oracle situation?

No. The archive still supplies the vendor input, but its generated `H5Oina_Test_Data.dream3d` output is no longer used as an oracle. The unit test now uses analytical values and independent reads of the input file.

`vv_work:ReadH5OinaDataFilter/exemplar_selforacle_check.txt` records 1,875 Euler elements that are bit-identical to the raw input. It also records the old `LatticeConstants` angle components in radians. Comparing with that output enforced D6 instead of detecting it. The vendor input has equal lattice angles, one cubic phase, and one scan, so it cannot expose the gamma-slot error, hexagonal-alignment errors, or scan-placement errors.

The replacement retains the real-file geometry, array-copy, Phase-widening, and ensemble checks. The analytical fixtures supply distinct angles, multiple phases, and multiple scans to detect the defects the vendor input cannot expose.
